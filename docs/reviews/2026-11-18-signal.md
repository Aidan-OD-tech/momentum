# /craft signal: feedback and status messages (2026-11-18)

Covers save states (the top-bar indicator), building, the error screens, the "Requirements updated" notice (R3 03), "Progress saved", Undo, and the brief character count. Each is checked for affordance, signifier, mapping and feedback. These are **recommendations, not decisions**. Nothing changes in M5; accepted items go to "M6 candidates" in [decisions.md](../decisions.md).

**Operating Conditions:** lost work + misplaced trust; laptop and split screen, interrupted; mixed skill, overwhelmed. Signals must land at a glance and can't rely on convention alone. Status that protects against lost work must be redundant (visible and announced).

**How this was checked:** the production build in Chrome at 1280×800 and 600×800 (screenshots `docs/evidence/screenshots/m5-*.png`), the DOM (roles and live regions) and the code. Screen-reader output was **not** heard; Aidan's VoiceOver script is in [accessibility.md](../evidence/accessibility.md).

## Wrong signal (the UI says something it shouldn't)

**[1] "Saved in this browser" in a stale tab.** With two tabs open, the old tab writes its old copy over the other tab's work and still shows "Saved in this browser". Verified in [/craft risk](2026-11-18-risk-pause-saving.md) item 1.
- User assumption: "everything I did is safe."
- Fix: keep the tabs in step (`storage` event). The indicator is then true again.

**[2] Error 03 "Try again in a moment" when rate limited.** A 429 shows the same Error 03 as a server failure. "A moment" can be up to 10 minutes (5 builds per IP per 10 minutes). In the sessions, several builds from one Wi-Fi network can reach it.
- Fix (M6): a separate line for `rateLimited`, e.g. "Too many plans were built from this network in the last few minutes. Try again in about 10 minutes." (development copy; Aidan writes the wording). Until then, Aidan avoids building plans himself just before a participant (feedback/README.md).

## Missing signal (the affordance exists, the cue doesn't)

**[3] Save status isn't announced.** `SaveIndicator` in `TopBar.tsx` is a plain `<p>`: "Saved in this browser" and "Couldn’t save in this browser" never reach a screen reader. This fails WCAG 4.1.3 (status messages) for the save failure, the one status that protects against lost work.
- Fix (M6): wrap the indicator in `role="status"`. The region must stay mounted so changes are read. Announce only when the state changes (to failed, or back to saved), not on every write.

**[4] Pasting over 12,000 characters cuts the brief silently.** The browser's `maxLength` keeps the first 12,000. The count reads "12,000 of 12,000 characters" and the live region says the limit was reached, but nothing says text was removed. A brief's end often holds the due date and submission rules. If those are cut, the plan misses them, and the student trusts the plan.
- Fix (M6): on a paste that would exceed the limit, say what happened, e.g. "Only the first 12,000 characters were kept. Check the end of your brief made it in." (development copy). Or let the paste in and show the over-limit error, which already exists ("Your brief is longer than 12,000 characters…").

**[5] Undo doesn't say what it undoes.** On step complete, the accessible name is just "Undo". Visually it sits beside "Step 2 will be here when you come back.", which is about something else. On the final check it sits beside "Step 6 is marked done.", which is clear.
- Fix (M6): an accessible name such as "Undo: mark step 1 as not done", or keep "Undo" and link it by `aria-describedby` to a short line ("Step 1 is marked done.") matching the final check's footer.

**[6] "Progress saved" may not be announced.** It is `role="status"`, but it appears with the new home screen, already filled in. Screen readers often skip a live region that arrives with its text. Focus moves to the h1 "Pick up where you left off", so the screen is announced, but probably not "Progress saved". **Not verified**: VoiceOver script step 4.

**[7] Why Start step 1 can't be pressed, for sighted users.** While an edit card is open, Start step 1 is grey (`aria-disabled`). The reason "Finish editing to start." is screen-reader text only. The open card is a fair visual hint, but the card can be off screen, since Start step 1 is at about 1,315 px.
- Fix (M6, optional): show the same line as a caption beside the button while it waits.

**[8] Brief entry doesn't say the draft is kept.** The draft is saved as the student types and survives a reload. No indicator shows before a plan exists (handoff decision 4). A student about to reload, or leaving mid-paste, can't know.
- Fix: none yet. Watch whether anyone hesitates. The error screens already say "Your text is still here."

## Weak signal (the cue is right but too quiet)

**[9] The save failure looks almost like success.** "Saved in this browser" is a 13 px caption in `text/tertiary` with a check icon, top right. "Couldn’t save in this browser" is the same size in `text/secondary`, without an icon. For an interrupted student, the difference between the two is a slight color shift in the corner of the screen. At 600 px the indicator wraps to two lines (`m5-working-step-600.png`).
- Fix (M6): give the failed state its own icon (`AlertIcon` exists) and keep it on one line. Optionally, repeat it near the work (risk item 3). Don't use color alone (DESIGN.md).

**[10] The brief text area's border is 1.48:1.** The box where the first action happens (paste) is drawn with `border/input` (#d4d4d4) on white, below the 3:1 non-text minimum (WCAG 1.4.11). The label and placeholder help, but the edge of the field is faint. The same token draws the deadline field, the step edit fields and the pause note. Known since M2, scheduled for M6.
- Fix (M6): a darker input border token (for example `text/tertiary` #737373, 4.7:1) for fields only; secondary buttons can keep the light border because their text identifies them.

## Working as intended (feedback lands)

- **Building:** heading focused ("Building your plan"), one honest line ("This usually takes under a minute.", preview runs 14.9–18.1 s), "Working on it" in `role="status"`, Cancel visible. No fake stages.
- **Errors 01–03:** Error 01 marks the field invalid, links the message and focuses the field. Errors 02 and 03 focus their heading and say "Your text is still here."
- **"Requirements updated":** a persistent `role="status"` container, filled on change. It shows only when something changed and says what didn't change ("Momentum hasn’t changed them.").
- **Character count:** visible only near the limit, read with the field, and announced once on crossing and once at the limit.
- **Mark complete and Finish for now:** each leads to a full screen that confirms it (step complete; home with "Progress saved").

# /craft scope: M3–M4 flows (2026-11-17)

Covers brief entry, plan building, plan review and editing, and the error screens. Read against PRODUCT.md, DESIGN.md, FEATURES.md, docs/product.md and the handoff ("By screen" 1–3, decisions 3–4, Error 01–03, R3 03–05). These are **recommendations, not decisions**: nothing here changes scope until Aidan accepts an item and it is logged in decisions.md.

**Operating Conditions:** lost work, then misplaced trust; laptop, split screen, interrupted; mixed skill and overwhelmed.
**Stage:** pre-launch course project with no users yet. The bar is "needed for the evaluation sessions and the case study?" Mixed, overwhelmed users weight flow simplicity heaviest.

The handoff already cut most of the usual overbuild, so the Cut list is mostly things to *not add* while building. No hour estimates are given; there is no basis for them.

## Cut (don't build)

1. **Staged building checklist (Setup 02).** One model request returns everything at once, so stages can't be observed. The handoff already says so: build R3 04, one indeterminate "Building your plan" state with no counts.
2. **Regenerate plan, or generating per step.** It conflicts with decision 3 ("never regenerate or quietly rewrite steps") and with Ryan's "generate once". If the plan is wrong, the student edits it, or goes back to brief entry with the brief kept.
3. **Reordering steps (drag or move up/down).** No named problem. The handoff lists add, edit and delete only. Reordering on a split-screen laptop is fiddly, and the student can delete and add instead.
4. **Editing the plan after starting.** MVP says review and edit *before* starting; the side panel's Plan tab stays read-only. Editing a plan mid-way with completed steps, notes and undo raises state questions the MVP doesn't need.
5. **Editing a requirement's kind (substantive/format/submission) in the UI.** It's an internal sort key (substantive first). Asking an overwhelmed student to classify requirements is homework. See Needs Aidan 2 for what a *new* requirement gets.
6. **Extra brief validation (minimum length, "doesn't look like a brief", language checks).** The handoff names one browser check, Error 01 for an empty submit. Anything the model can't use surfaces as Error 02 from a real response.
7. **Auto-retry and backoff on failure.** Error 03 with a "Try again" the student presses is enough. Silent retries make a slow failure look like a hang.
8. **An "Example brief" button for evaluation.** Hand participants the brief text to paste instead. Pasting is the real task (evaluation task 1), and it keeps a demo path out of the product. Revisit only if a session shows it's needed.

## Simplify (keep, at less depth)

9. **Deadline input.** Use one native `datetime-local` field, optional, with no custom picker. It overrides the deadline the model finds in the brief (handoff). Leave it blank and the brief's deadline is used if one is found.
10. **Error screens.** Build one Error card component with three messages, not three screens. Error 01 is inline on brief entry. Errors 02 and 03 use the same card with the brief kept and two actions: Try again and Edit brief. Timeouts and rate limits fold into Error 03.
11. **Step editing (Setup 04).** One step at a time, editing title, what to do, "Done when" and the estimate stepper (5-minute increments, minimum 5, labeled approximate). Generated-only fields (`intro`, `completedSummary`) aren't editable. Start step 1 stays disabled while an edit is open (handoff). *Check against Setup 04 in Figma; that frame isn't in `docs/reference/figma/`.*
12. **Adding a step.** Add at the end only, opening straight into the same edit card. No "insert above/below".
13. **Requirements editing (Setup 05).** Edit labels, add and delete, then show the R3 03 notice and its "Review steps" link. The notice is plain text with no undo history and no step diffing.
14. **"Your brief is sent to an AI service" disclosure.** Use one plain line on brief entry near the button. No consent modal, privacy page or settings. The claim must stay true: progress stays in the browser, the brief text is sent to the model provider (MOMENTUM_CONTEXT).
15. **Structured output handling (M4).** Make one request and validate the response against the plan shape with one small, readable check. Anything missing or wrong becomes Error 02; there is no repair pass and no partial plans.

## Keep (right depth already)

16. Pasted-text brief entry, with the save indicator hidden until a plan exists (R3 05).
17. Plan review: summary, requirements as chips (including the substantive ones), steps, total estimate as a sum, and Start step 1.
18. The brief side panel from plan review (Panel 03), reusing the existing Sheet.
19. The "Requirements updated" notice and the rule that requirement edits change the checklist, never the steps.
20. The brief kept on every failure path.
21. Server-side generation with the API key never in the browser.
22. The preview deploy (required by the course).

## Needs Aidan

1. **Deleting a step.** Lost work is the primary risk, but a confirmation dialog adds a step for overwhelmed users. Recommend: Delete only inside the edit card (already a deliberate mode) with no extra dialog. Confirm, or bring it to `/craft risk`.
2. **Kind of a newly added requirement.** It needs one for ordering and the checklist. Recommend: `substantive`, so it lists first and is never hidden among format items. Alternative: put new ones last.
3. **Cost guard on the public generation route.** Not a scope cut but a risk: a deployed endpoint holding the API key can be called by anyone. Recommend a maximum brief length checked on the server, and taking the rest to `/craft risk` before the M3 preview deploy.

## Summary

Cut 8 · Simplify 7 · Keep 7 · 3 for Aidan. None of the cuts removes something in the handoff; each one is a guard against adding something it doesn't ask for.
